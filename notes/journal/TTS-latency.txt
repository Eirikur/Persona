● I'd try both, but only as standalone benchmark scripts, and I wouldn't change
  the stack yet. You wrote "Qwen STT", but I assume you meant Qwen3-TTS, so

  Qwen3-TTS

  - Cloning: It does voice cloning two ways. The x-vector mode takes just a
    sample. The ICL mode gives closer cloning but needs the exact transcript of
    the reference clip. That adds a step to your tweak-the-sample workflow.
  - Streaming: It streams audio in about 80 ms frames, which is the kind of
    time-to-first-sound fix you're after. The 81 ms onset and 0.108 RTF in the
    README were measured on an RTX 4090.
  - CPU: Their own docs say CPU realtime performance is not a supported
    guarantee. A CPU build is only "a locally built wheel is possible".
  - AMD: They list AMD/Vulkan as not part of the supported release. The
    underlying ggml library has a Vulkan backend, so a Strix Halo build might
    work, but I found no evidence anyone has done it.
  - QwenCpuEngine: The GitHub page summary mentioned it, but it doesn't exist
    anywhere in your 0.8.3 checkout. Treat it as unverified until we see it in a
    release.
  - Other CPU numbers: A blog claims 3–5x slower than real time on CPU. That is
    probably the PyTorch reference model, not this 0.6B quantized build, so it
    doesn't settle anything either way.
  - Licenses: The model and the runtime are Apache/MIT.

  Coqui (XTTS-v2)

  - Maintenance: The original company shut down in 2024, but Idiap maintains a
    fork as the coqui-tts package. Version 0.27.5 came out in January 2026, so
    it's alive. RealtimeTTS's CoquiEngine is built on it.
  - Cloning: It clones from a short WAV with no transcript, so it fits your
    workflow best.
  - CPU: It runs on CPU and streams chunks. Its speed on this box is unknown,
    and I'd guess it's the same order of magnitude as Chatterbox, not a big win.
  - Quality: I'd expect it to sound worse than Chatterbox.
  - License: The weights are non-commercial only (CPML). That's the same kind of
    question as your 2026-09-23-voice-sample-legal.md, so it's fine for private
    use.
  - AMD: The CPU path doesn't touch ROCm, so it's the lowest-risk install of the
    two.

  PocketTTS

  You didn't ask about this one. It's a small English-only model built for CPU,
  and it does voice cloning from a WAV. It's the only engine in that list
  designed for exactly your constraint. I haven't looked at its quality.

  What I'd do

  1. Chunking first. Your idea 2 in notes/2026-09-24-latency-ideas.md is cheap
     and needs no new engine. It fixes the "did it hear me?" confusion because
     sound starts after the first sentence.
  2. Then a benchmark script outside the stack. It would be a standalone uv run
     script that renders the same three sentences with your Sal sample. It would
     report time-to-first-audio and seconds per word for Chatterbox, then
     Coqui, then PocketTTS. Qwen would come last, since it needs a native build
     and the transcript step. That gives real numbers on this machine, and I'd
     save the WAVs so you can judge the sound.
  3. Only then think about a second engine. Adding one behind
     persona_speech_output.py for multi-persona (say, a fast engine for
     secondary personas) is a design decision for after the numbers.
